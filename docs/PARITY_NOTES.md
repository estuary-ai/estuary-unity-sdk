# Unity SDK — Parity Notes

Per-feature implementation detail, rationale, and hard-won behavioural notes for the
Estuary Unity SDK. `CLAUDE.md` carries the scannable status table and links here.

These notes record **why** each feature behaves the way it does — race conditions that were
actually hit, deliberate deviations from the other SDKs, and traps that look like bugs.
Per the SDK Authoring Protocol, platform quirks are sacred: do not remove or contradict
anything here without testing on real hardware.

Required conversation features and the optional features below are implemented. Explicit exclusions: Audio2Face, Lens-only encounters, web debug metrics, and niche batch/document REST wrappers.

- text_chat: Implemented
- voice_websocket: Implemented
- voice_livekit: Implemented (requires LiveKit SDK). **Warm start:** the gateway allocates its bot pre-join + STT on a `livekit_token` request (voice intent), never at auth. `EstuaryManager` therefore emits the `livekit_token` request at voice intent even when an embedded session_info token is held: the embedded token still wins the race for the client-side room join (no round-trip penalty), while the request pre-warms the server's bot join. The duplicate token response is absorbed by an idle-state guard in `HandleLiveKitTokenReceived` (only auto-connects from Disconnected/RequestingToken, so the room is never bounced). **First-chunk-muted race (fixed):** bot voice is one continuous WebRTC track played through a single `AudioSource`; interrupts silence it via `volume=0` (Stop() would break the AudioStream's `OnAudioFilterRead` pipeline), and it's unmuted only when the next message's `bot_voice` metadata is processed in `NotifyAudioChunk`. Because that metadata (Socket.IO, main-thread-queued) and the actual audio (WebRTC, audio thread) travel independent paths, a new response's first chunk could play while still muted. `LiveKitVoiceManager` runs a bounded safety-net that, in `ProcessMainThreadQueue`, auto-unmutes after `AutoUnmuteDelaySeconds` (from `EstuaryConfig.botAudioAutoUnmuteMs`, default 250ms) if no new-message metadata has disarmed it first. The net is armed only when a NEW outbound response is actually expected — `EstuaryManager` calls `NotifyResponseExpected()` at turn dispatch (user final transcript, non-textOnly text/say_line, camera image send), and a mute that lands after such a dispatch arms it too — NOT on the interrupt mute itself: arming on every interrupt made the OLD response's WebRTC tail audibly resume 250ms after a barge-in (new-response metadata takes ~1s+). An interrupt with no following turn now stays muted until the next response's metadata arrives; the delay only bounds how long the NEXT response's first chunk can be clipped, so too high re-introduces clipping. Unity-LiveKit-specific (the other SDKs don't use this AudioStream-volume-mute pattern).

  **LiveKit v2.1 disconnect:** `Room.Disconnect()` now fires `Room.Disconnected` synchronously for client-initiated teardown. `LiveKitVoiceManager` forwards that callback once with `"client disconnect"` when `room.DisconnectReason` is `ClientInitiated`; the manager uses that reason to avoid treating a local leave as an unexpected transport loss. `DisconnectAsync()` emits the local event itself only if the Room callback did not fire, for projects that still have an older LiveKit version installed.
- voice_push_to_talk: Implemented (contract v1.11, SCRUM-220) — server-side turn handling on BOTH transports. The mic declares PTT via `IsPushToTalkMode` (`pushToTalkEnabled` only); an assigned `pushToTalkKey` is ignored while the checkbox is off. The Inspector disables the key field until PTT is enabled. Existing scenes that set only the key must enable the checkbox. `EstuaryManager` mirrors it onto `EstuaryClient.SessionTurnMode` before every declaration point (`livekit_token`, `livekit_join`, `start_voice` — synced again at `HandleLiveKitConnected` for the embedded-token cold path). Press = `client_interrupt` + `start_voice {turn_mode}`; release = `stop_voice`; both are guard-free (`Notify PushToTalk*Async` skip `_isVoiceModeActive` — on LiveKit+PTT that flag is false before the first press and flips true after it, since every press's `start_voice` on an already-active session replies `voice_started {"already_active": true}` and `HandleVoiceStarted` sets the flag; a guard would swallow either the first press or every later one). Because the flag flips true after the first press, `EndVoiceSession`'s `StopVoiceModeAsync` guard subsequently passes too, so LiveKit+PTT sessions also emit a phantom session-end `stop_voice` once a press has occurred — verified harmless (the server flushes an empty buffer and answers `voice_stopped {already_stopped}`). Consequently `OnVoiceStarted`/`OnVoiceStopped` pulse once per press/release rather than once per session (the server sends `voice_stopped {ptt_turn_end}` on each release). SIX deliberate behaviors: (1) **phantom-press suppression** — `EstuaryManager.StartVoiceModeAsync` skips the session-start `start_voice` on LiveKit+PTT (it would hold the server's turn gate with no matching release; mirrors the Python reference); (2) **PTT starts muted** — `StartLiveKitRecording` mutes immediately after publish in PTT mode (previously the track ran hot until the first press/release cycle); (3) **interrupt-on-press** — a press stops in-flight bot speech immediately; server speech detection remains responsible for continuous-mode barge-in; (4) **press requires an active voice session** — `PushToTalkPress()` is inert unless `targetCharacter.IsVoiceSessionActive` (a bound key in text mode must not interrupt the bot or open a billable STT stream); (5) **teardown is transport-gated, not IsRecording-gated** — the muted PTT steady state keeps `IsRecording` false, so `StopRecording()` always runs the (idempotent) LiveKit teardown when a manager is attached, and a mid-hold teardown sets `_pttWasPressed = true` so a still-held key can't phantom-re-press; (6) **spurious-unmute suppression** — `OnLiveKitMuteStateChanged` ignores an unmuted callback while PTT-idle (guards the publish/mute enqueue race at muted session start). WebSocket PTT gates chunks on `_pttHeld` (not raw `Input.GetKey`), so programmatic `PushToTalkPress()`/`PushToTalkRelease()` (for touch/XR) work on both transports. `StopRecording()` releases a held button so a mid-hold teardown can't leave the server gate held. Continuous mode stays wire-identical to pre-v1.11 (`null` payloads — JsonUtility can't omit fields, so the payload object is only constructed in PTT mode). Wire-emission tests: `Tests/Editor/PushToTalkEmissionTests.cs` via the internal `AttachSocketForTest` seam.
- interrupts: Implemented — continuous-mode barge-in comes from server-confirmed speech on both transports. `EstuaryManager.HandleInterrupt` signals the LiveKit playback manager and routes the event to `EstuaryCharacter.HandleInterrupt`, which stops playback and clears the partial response. Local RMS VAD, the parallel Unity mic capture, WebSocket silence gating, and `EstuaryAudioSource` microphone-driven auto-interrupt were removed. Push-to-talk still interrupts on press.
- audio_playback_tracking: Implemented
- vision_camera: Implemented — full VLM round-trip. `SendCameraImage(imageBase64, mimeType, requestId?, text?)` (client → manager → character) emits `camera_image`; the server's proactive `camera_capture` request surfaces as `OnCameraCaptureRequested(CameraCaptureRequest)`. (Distinct from `EstuaryWebcam`, which streams continuous world-model video; this is the on-demand vision path. Added 2026-07-15 for parity with the TS/Python/Lens SDKs — the prior "Implemented" claim was stale, there was no code.)
- client_action (contract v1.10): Implemented — typed in-world action delivery via native LLM function calling (SCRUM-202), superseding the legacy inline XML `<action .../>` tags that rode inside `bot_response` text. **Requires the opt-in:** the server serves the retired tag path to any client that doesn't declare `capabilities.client_action: true`, so this SDK forces that flag on every auth payload (see session_capabilities below). The text handler never executes XML tags, including stray tags in generated prose. `EstuaryClient` handles `client_action` `{name, arguments, message_id, chunk_index, timestamp}` and fires `OnClientAction(ClientActionEvent)`; `EstuaryManager` routes to the active `EstuaryCharacter` (same chain as bot_response), which converts to the existing `AgentAction` model and fires the SAME public callbacks as the legacy parse path (`OnActionReceived` C# event + `onActionReceived` UnityEvent) — integrators and `EstuaryActionManager` see no API change. **Fire-on-arrival semantics** per the contract: the action triggers as soon as the event arrives, not synchronized to TTS playback position. Argument values are stringified into `AgentAction`'s string parameter dictionary (numbers invariant-culture, booleans lowercase "true"/"false") to match legacy XML-attribute behavior — integrators keep using the typed getters (`GetParameterInt/Float/Bool`). Payload parsing uses Newtonsoft (`ClientActionEvent.FromJson`) because the dynamic-keyed `arguments` map is beyond JsonUtility. `EstuaryCharacter` forwards `bot_response.text` unchanged; the worker strips stray action tags on typed sessions before delivery. The Inspector text-stripping switch and executable XML parsing have been removed. `ActionParser.StripActions` remains an opt-in utility for historical text.

- session_capabilities: Implemented — the auth payload carries `capabilities {version, camera, microphone, speaker, client_action}`. The device fields are a per-session declaration (server hides tools that need an absent capability), configured via the EstuaryConfig `deviceHas*` toggles and defaulting all-true (identical to omitting them). The SDK always sends a non-null object because Unity's JsonUtility serializes a null nested object as all-false. `client_action` (contract v1.10) is NOT a device field: it declares that this build speaks the typed action protocol, the server defaults it to **false** when absent, and `EstuaryClient.BuildCapabilitiesPayload()` forces it true on a copy so an integrator-supplied `SessionCapabilities` can't drop the session onto the retired XML tag path. As of the v1.10 pass every SDK sends capabilities (TS, Lens, Python and Unreal included). Verified + wire-shape-locked 2026-08-03 (SCRUM-141): `Tests/Editor/AuthPayloadTests.cs` reflects over `AuthenticateData` and asserts `SessionCapabilities` defaults, so a field rename or default flip can't silently break the contract.
- memory_push: Implemented — handles `memory_updated`, fires `OnMemoryUpdated(MemoryUpdatedEvent)` (client → manager → character). `MemoryData` uses camelCase keys (matching `Memory.to_dict()`). Matches TS/Python.
- motive_push (contract v1.7): Implemented — handles `motive_updated` (snake_case, arrives immediately before the paired `memory_updated`), fires `OnMotiveUpdated(MotiveUpdatedEvent)` through the same client → manager → character chain as memory_push (C# events + an inspector UnityEvent on the character). `AgentResponse` gains a `Motive` field, but note the legacy `/api/agents` LIST payload deliberately omits it (privacy) — expect null from `GetAgents`; the seed motive is available through `GetCharacter`. The owner-only `GetCharacterMotive`, `SetCharacterMotive`, and `ResetCharacterMotive` methods wrap `GET/PATCH/DELETE /api/v1/characters/{id}/motive`.
- voice_timeout: Implemented — server voice-lane idle release (SDK_CONTRACT.md): after no user speech for `VOICE_IDLE_TIMEOUT_S` the server emits `voice_timeout`, deletes the LiveKit room / closes STT, and KEEPS the socket (text keeps working; no disconnect follows — never wired into reconnect suppression). `EstuaryClient` clears the voice-mode gate and fires `OnVoiceTimeout(VoiceTimeoutData)`; `EstuaryManager` disposes the local LiveKit room WITHOUT `livekit_leave` (the room is already gone server-side; its Disconnected event during this teardown is expected, not a call failure) and forwards to `EstuaryCharacter`, which stops the mic and clears `IsVoiceSessionActive` so the next `StartVoiceSession()` is a fresh session. Recommended UX is the auto-mute illusion (mic shows muted; unmute = `StartVoiceSession()`). Belt-and-braces: any non-client LiveKit room disconnect also clears stale voice state via `HandleVoiceTransportClosed`.
- session_timeout: Implemented at EVERY reconnect-owning layer (Lens lesson 7/8: socket-layer suppression alone is insufficient) — `EstuaryClient.HandleSessionTimeout` fires `OnSessionTimeout(SessionTimeoutData)` and flags the disconnect that follows so the client's auto-reconnect is suppressed; the event is forwarded client → manager → character, and `EstuaryCharacter` sets its own `_serverEndedSession` flag so its component-level `autoReconnect` also skips the reap disconnect (it previously looped: reconnect → re-auth → billed voice resources → reaped again). Both flags clear on explicit connect. Resuming requires an explicit `ConnectAsync`/`Connect()` driven by user intent, per SDK_CONTRACT.md.
- session_rejected: Implemented — handles `session_rejected` {reason, cap, share_token_id}, fires `OnSessionRejected(SessionRejectedData)` (client → manager → character). The server disconnects immediately after, so the SDK sets the same `_serverEndedSession` suppression flag as session_timeout at BOTH the client and character layers — otherwise the trailing disconnect would auto-reconnect straight back into the concurrent-session cap in a loop. (Added 2026-07-15, upgrading the prior "impl deferred" status; the reconnect-loop was a real latent bug — no other SDK handles this event either.)
- moderation events: Implemented. `moderation_warning` and `moderation_flag` pass through Client → Manager → Character on the main thread. Termination latches reconnect suppression in both owners until explicit Connect, stops local audio/mic, and drops queued content from the closed session. Redaction records a message-ID tombstone before main-thread dispatch, rejects later text/audio/actions/media for that ID, clears matching PCM, and replaces `CurrentPartialResponse` only when its text ID matches. Integrators must redact their own historical UI/media using `OnModerationFlag`; BasicChatDemo demonstrates this. A flag for an old response must never mute a newer LiveKit response.
- input_limits / rate_limited: `OnServerError(ServerError)` exposes both the machine code and human message while preserving `OnError(string)`. Never auto-retry these failures. REST errors include status and the full response detail, including missing API-key scopes.
- character_model_loading: Implemented — runtime download + instantiation of a character's Estuary-generated 3D model (GLB) as a GameObject. `EstuaryModelLoader` (component) exposes `LoadForAgent(agentId)` and `LoadFromUrl(modelUrl, provider)`; it reuses `EstuaryHttpClient` (`GetCharacter`/`PollModelStatus`/`DownloadGlb`) to resolve the ready GLB URL, downloads it, and instantiates via an **optional** glTF importer. The importer follows the LiveKit optional-dependency pattern exactly: `IEstuaryModelLoader` + `ModelLoaderBridge` (core) with a glTFast-backed impl in the define-gated `Estuary.glTFast` assembly (`ESTUARY_GLTFAST`, set by a `versionDefine` on `com.unity.cloud.gltfast`/`com.atteneder.gltfast`) — so the core assembly compiles with zero errors when glTFast is absent, and the loader surfaces a clear "install a glTF importer" error at runtime instead. Install via `Estuary > Install glTF Importer (glTFast)`. Provider-aware orientation offset (`AgentResponse.modelProvider` drives it): Tripo GLBs import facing -X in Unity, so the default `tripoRotationOffset` is `(0, -90, 0)` to face +Z — **verified live** against a real Tripo character (renders + textures + faces camera). Meshy default is identity (untested in Unity, corroborated by the frontend). Plus optional height normalization. Mirrors the web frontend's `Model3DViewer` flow (poll status → load textured `modelUrl`, fall back to `modelPreviewUrl` on `texture_failed`). glTFast imports skeletal clips with AnimationMethod.Legacy. `EstuaryClipPlayer` maps typed actions to an exact clip name or a unique colon-delimited suffix; idle/walk/run loop, other clips return to idle. Generation accepts `rigged: true`; polling includes posing, rig_checking, rigging, animating and treats rig_failed/animation_failed as partial success only with a usable model URL. Audio2Face is separate and excluded. **Verified end-to-end** 2026-07-16 in `estuary_unity_testing` against prod: GetAgents → DownloadGlb (~1.75MB) → glTFast import → instantiated `EstuaryCharacterModel`.
- simulation motives (contract v1.7): Implemented — `SimulationCharacterSpec`/`SimulationWorldCharacter` gain `Motive` (seed, optional ctor arg), `SimulationInstance` gains `CharacterMotives` (live per-run map), and the `/sim-v1` stream + `EstuarySimulation` component surface `OnMotiveUpdated(characterId, motive)` (`simulation_motive_updated`, wired like `OnWorldViewUpdated`). `EstuarySimulationApi.SetCharacterMotive(instanceId, characterId, motive, ...)` wraps the director override PATCH. `AddCharacter(..., motive: ...)` passes an optional seed motive.
- simulation (v1): Implemented — full public Simulation API (SDK_CONTRACT.md §REST API — Simulation (v1), contract v1.4–1.6). Three layers: `EstuarySimulationApi` (Core; coroutine REST client for `/api/v1/simulation/*` — worlds/instances CRUD, pair + group conversation triggers, events/lore/world-view/transcript reads; reuses `EstuaryHttpClient`'s auth internals so Bearer-token-vs-X-API-Key behavior is identical, and surfaces the server's `{"detail": ...}` body in error callbacks), `EstuarySimulationStream` (Core; `/sim-v1` Socket.IO namespace client reusing the SDK's built-in Socket.IO transport with auth `{apiKey, instanceId}` — streams `simulation_started/_message/_tool_call/_lore/_world_view/_complete/_error` for immediate triggers, main-thread queue + bounded reconnect like EstuaryClient), and `EstuarySimulation` (Component; owns both, pumps the stream queue in Update, exposes C# events + `TriggerConversation`/`TriggerGroupConversation`/`FetchWorldView`/`FetchLore` conveniences). Wire models in `Models/SimulationModels.cs` (Newtonsoft, camelCase `JsonProperty`, grouped in one file like AgentResponse.cs). Notes: the `/sim-v1` stream REQUIRES an API key (no Firebase token path server-side); scheduled (engine-processed) events do NOT stream — poll `ListEvents`; the world-view document arrives both as the `simulation_world_view` stream event and via `GetWorldView` REST (markdown null until the first conversation completes); request bodies serialize with NullValueHandling.Ignore because the server forbids unknown fields and defaults omitted ones. **Session isolation (contract v1.6):** sim lore/relationships/transcripts/world-view are per-instance, but remember-tool memories are keyed `(character, playerId)` and shared with live chat — so the component has a `worldId` field plus a `Destroy World On End` inspector toggle: `EndWorld()` tears down the stream and (when toggled) DELETEs the world server-side (v1.6 server purges instances, transcripts, AND memories), firing `OnWorldDestroyed`; a runtime `OnDestroy` fallback fires the DELETE fire-and-forget with the raw X-API-Key path (no coroutines during teardown; API-key-only because a TokenProvider can't resolve synchronously and falling back would escalate access; may be dropped on app quit — EndWorld() at a controlled moment is the guaranteed path). `ClearWorldMemories()` (component + Api, DELETE /worlds/{id}/memories → `SimulationWorldMemoriesCleared`) is the soft reset: wipes only sim-created memories, keeps the world/instances/lore/transcripts, never touches live-chat memories.
- turn_metrics: Not consumed (web-debug only) — backend emits this OPTIONAL/debug event (SDK_CONTRACT.md contract v1.2) carrying per-response voice-latency timings for the web chat latency gizmo; no Unity handler needed. Contract v1.2 adds an optional/nullable `speech_end_ms` field (predictive-turn head-start metric) and v1.12 adds an optional/nullable `tts_engaged_ms` field (when TTS synthesis started, vs. `tts_first_audio_ms` when its first byte arrived); both are additive and do not change the decision to ignore the event.
- animation_stream (`bot_animation`): Not implemented. Audio2Face is explicitly excluded from this parity pass. The existing opt-in remains for compatibility, but Unity does not consume/render those frames.
- stt_config (`stt_provider` / `stt_language_hints` / `stt_context_terms`, contract v1.14): Not applicable — STT runs entirely gateway-side. The SDK ships 16kHz PCM and receives transcripts; which engine transcribes it (Deepgram Flux vs Soniox v5), which languages are hinted, and the character's custom vocabulary are per-character settings edited in the dashboard. `AgentResponse` now exposes these configuration fields for REST reads; a character configured for Soniox v5 with vocabulary terms behaves identically on the wire (SCRUM-232).
- encounter: Not implemented — the 2-character agent-to-agent Encounter (`subscribe_encounter` / `encounter_*` + `POST /api/encounters`) is Lens-Studio-only at MVP per SDK_CONTRACT.md. Add here if/when Encounter is promoted beyond the Lens SDK.

- REST parity: `EstuaryHttpClient` uses one request path for auth, errors, escaping, uploads and simulation. Every API request identifies `estuary-unity-sdk/<version>`; asset downloads intentionally carry no API credentials. Firebase provider failure never falls back to the API key. Share redemption is anonymous and share creation uses Bearer auth. All 2xx statuses, including empty 204, are accepted. Legacy `GetAgents` remains unpaginated; `ListCharacters` is the canonical paginated replacement.
- HTTP turns: `Turn` is text-only request/response; `StreamTurn` incrementally decodes UTF-8 NDJSON, preserves event order, surfaces rich results separately, and requires a terminal `turn_completed`. Errors, malformed events and incomplete streams call onError without retry. Disposing the request iterator disposes its UnityWebRequest.
- Delegation/media: typed `DelegationUpdate` and `ApiEndpointResult` propagate unchanged on the main thread. URLs are data; the SDK does not launch authorization URLs or automatically load remote media. The app owns presentation and any HTTPS media validation.
- WebSocket playback: `BotVoice.IsFinal` survives parsing, including empty terminators. A message is acknowledged only after its final flag and its samples have passed the local DSP render deadline. Temporary buffer underruns cannot trigger completion; short final clips bypass the normal prebuffer threshold. Single-packet legacy filler interjections are treated as complete audio. Raw PCM callers must call `MarkAudioComplete(messageId)`. Disconnect resets tracking and PCM. Subscriber callbacks run after state cleanup so they can safely enqueue a new response.
- LiveKit bot attributes: optional `ILiveKitBotStateSource` exposes `CurrentBotSpeakingState` and `OnBotSpeakingStateChanged`; missing `estuary.message_id` becomes an empty string. This is a server-state hint, not a local audio playback clock. Existing audio synchronization and platform workarounds remain intact.
- Tests: `Tests/Fixtures/rest.json` is vendored from `../sdk-conformance/rest.json`; keep both and the backend fixture in sync. Run EditMode `Estuary.Tests` in a testable/embedded SDK package. Cover contract requests and response decoding, auth failures, NDJSON, scoped moderation, typed-only actions, text boundaries, completion tracking and rig clip resolution. Optional LiveKit/glTFast assemblies must also compile. Hardware audio and rendered clips still need device smoke testing.
