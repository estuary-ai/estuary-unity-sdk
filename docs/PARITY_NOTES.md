# Unity SDK — Parity Notes

Per-feature implementation detail, rationale, and hard-won behavioural notes for the
Estuary Unity SDK. `CLAUDE.md` carries the scannable status table and links here.

These notes record **why** each feature behaves the way it does — race conditions that were
actually hit, deliberate deviations from the other SDKs, and traps that look like bugs.
Per the SDK Authoring Protocol, platform quirks are sacred: do not remove or contradict
anything here without testing on real hardware.

All `REQUIRED` features and the applicable `OPTIONAL` features from SDK_CONTRACT.md are implemented (web-debug-only events like `turn_metrics` are intentionally not consumed — see below):

- text_chat: Implemented
- voice_websocket: Implemented
- voice_livekit: Implemented (requires LiveKit SDK). **Warm start:** the gateway allocates its bot pre-join + STT on a `livekit_token` request (voice intent), never at auth. `EstuaryManager` therefore emits the `livekit_token` request at voice intent even when an embedded session_info token is held: the embedded token still wins the race for the client-side room join (no round-trip penalty), while the request pre-warms the server's bot join. The duplicate token response is absorbed by an idle-state guard in `HandleLiveKitTokenReceived` (only auto-connects from Disconnected/RequestingToken, so the room is never bounced). **First-chunk-muted race (fixed):** bot voice is one continuous WebRTC track played through a single `AudioSource`; interrupts silence it via `volume=0` (Stop() would break the AudioStream's `OnAudioFilterRead` pipeline), and it's unmuted only when the next message's `bot_voice` metadata is processed in `NotifyAudioChunk`. Because that metadata (Socket.IO, main-thread-queued) and the actual audio (WebRTC, audio thread) travel independent paths, a new response's first chunk could play while still muted. `LiveKitVoiceManager` runs a bounded safety-net that, in `ProcessMainThreadQueue`, auto-unmutes after `AutoUnmuteDelaySeconds` (from `EstuaryConfig.botAudioAutoUnmuteMs`, default 250ms) if no new-message metadata has disarmed it first. The net is armed only when a NEW outbound response is actually expected — `EstuaryManager` calls `NotifyResponseExpected()` at turn dispatch (user final transcript, non-textOnly text/say_line, camera image send), and a mute that lands after such a dispatch arms it too — NOT on the interrupt mute itself: arming on every interrupt made the OLD response's WebRTC tail audibly resume 250ms after a barge-in (new-response metadata takes ~1s+). An interrupt with no following turn now stays muted until the next response's metadata arrives; the delay only bounds how long the NEXT response's first chunk can be clipped, so too high re-introduces clipping. Unity-LiveKit-specific (the other SDKs don't use this AudioStream-volume-mute pattern).
- voice_push_to_talk: Implemented (contract v1.11, SCRUM-220) — server-side turn handling on BOTH transports. The mic declares PTT via `IsPushToTalkMode` (`pushToTalkKey` set OR `pushToTalkEnabled`); `EstuaryManager` mirrors it onto `EstuaryClient.SessionTurnMode` before every declaration point (`livekit_token`, `livekit_join`, `start_voice` — synced again at `HandleLiveKitConnected` for the embedded-token cold path). Press = `client_interrupt` + `start_voice {turn_mode}`; release = `stop_voice`; both are guard-free (`Notify PushToTalk*Async` skip `_isVoiceModeActive` — on LiveKit+PTT that flag is false before the first press and flips true after it, since every press's `start_voice` on an already-active session replies `voice_started {"already_active": true}` and `HandleVoiceStarted` sets the flag; a guard would swallow either the first press or every later one). Because the flag flips true after the first press, `EndVoiceSession`'s `StopVoiceModeAsync` guard subsequently passes too, so LiveKit+PTT sessions also emit a phantom session-end `stop_voice` once a press has occurred — verified harmless (the server flushes an empty buffer and answers `voice_stopped {already_stopped}`). Consequently `OnVoiceStarted`/`OnVoiceStopped` pulse once per press/release rather than once per session (the server sends `voice_stopped {ptt_turn_end}` on each release). SIX deliberate behaviors: (1) **phantom-press suppression** — `EstuaryManager.StartVoiceModeAsync` skips the session-start `start_voice` on LiveKit+PTT (it would hold the server's turn gate with no matching release; mirrors the Python reference); (2) **PTT starts muted** — `StartLiveKitRecording` mutes immediately after publish in PTT mode (previously the track ran hot until the first press/release cycle); (3) **interrupt-on-press** — a press stops in-flight bot speech; this can double-fire with the local-VAD interrupt path, which is accepted (interrupts are idempotent server-side); (4) **press requires an active voice session** — `PushToTalkPress()` is inert unless `targetCharacter.IsVoiceSessionActive` (a bound key in text mode must not interrupt the bot or open a billable STT stream); (5) **teardown is transport-gated, not IsRecording-gated** — the muted PTT steady state keeps `IsRecording` false, so `StopRecording()` always runs the (idempotent) LiveKit teardown when a manager is attached, and a mid-hold teardown sets `_pttWasPressed = true` so a still-held key can't phantom-re-press; (6) **spurious-unmute suppression** — `OnLiveKitMuteStateChanged` ignores an unmuted callback while PTT-idle (guards the publish/mute enqueue race at muted session start). WebSocket PTT gates chunks on `_pttHeld` (not raw `Input.GetKey`), so programmatic `PushToTalkPress()`/`PushToTalkRelease()` (for touch/XR) work on both transports. `StopRecording()` releases a held button so a mid-hold teardown can't leave the server gate held. Continuous mode stays wire-identical to pre-v1.11 (`null` payloads — JsonUtility can't omit fields, so the payload object is only constructed in PTT mode). Wire-emission tests: `Tests/Editor/PushToTalkEmissionTests.cs` via the internal `AttachSocketForTest` seam.

- client_action (contract v1.10): Implemented — typed in-world action delivery via native LLM function calling (SCRUM-202), superseding the legacy inline XML `<action .../>` tags that rode inside `bot_response` text. **Requires the opt-in:** the server serves the retired tag path to any client that doesn't declare `capabilities.client_action: true`, so this SDK forces that flag on every auth payload (see session_capabilities below). Without it the events never arrive and the dormant `ActionParser` becomes the only action path again. `EstuaryClient` handles `client_action` `{name, arguments, message_id, chunk_index, timestamp}` and fires `OnClientAction(ClientActionEvent)`; `EstuaryManager` routes to the active `EstuaryCharacter` (same chain as bot_response), which converts to the existing `AgentAction` model and fires the SAME public callbacks as the legacy parse path (`OnActionReceived` C# event + `onActionReceived` UnityEvent) — integrators and `EstuaryActionManager` see no API change. **Fire-on-arrival semantics** per the contract: the action triggers as soon as the event arrives, not synchronized to TTS playback position. Argument values are stringified into `AgentAction`'s string parameter dictionary (numbers invariant-culture, booleans lowercase "true"/"false") to match legacy XML-attribute behavior — integrators keep using the typed getters (`GetParameterInt/Float/Bool`). Payload parsing uses Newtonsoft (`ClientActionEvent.FromJson`) because the dynamic-keyed `arguments` map is beyond JsonUtility. The legacy text-tag parser (`ActionParser` in `EstuaryCharacter.HandleBotResponse`) is **retained but dormant** during the deprecation window — the server no longer instructs models to emit tags, so it only fires on stray tags; remove in a follow-up release per SDK_CONTRACT.md migration notes.

- session_capabilities: Implemented — the auth payload carries `capabilities {version, camera, microphone, speaker, client_action}`. The device fields are a per-session declaration (server hides tools that need an absent capability), configured via the EstuaryConfig `deviceHas*` toggles and defaulting all-true (identical to omitting them). The SDK always sends a non-null object because Unity's JsonUtility serializes a null nested object as all-false. `client_action` (contract v1.10) is NOT a device field: it declares that this build speaks the typed action protocol, the server defaults it to **false** when absent, and `EstuaryClient.BuildCapabilitiesPayload()` forces it true on a copy so an integrator-supplied `SessionCapabilities` can't drop the session onto the retired XML tag path. As of the v1.10 pass every SDK sends capabilities (TS, Lens, Python and Unreal included). Verified + wire-shape-locked 2026-08-03 (SCRUM-141): `Tests/Editor/AuthPayloadTests.cs` reflects over `AuthenticateData` and asserts `SessionCapabilities` defaults, so a field rename or default flip can't silently break the contract.
- memory_push: Implemented — handles `memory_updated`, fires `OnMemoryUpdated(MemoryUpdatedEvent)` (client → manager → character). `MemoryData` uses camelCase keys (matching `Memory.to_dict()`). Matches TS/Python.
- motive_push (contract v1.7): Implemented — handles `motive_updated` (snake_case, arrives immediately before the paired `memory_updated`), fires `OnMotiveUpdated(MotiveUpdatedEvent)` through the same client → manager → character chain as memory_push (C# events + an inspector UnityEvent on the character). `AgentResponse` gains a `Motive` field, but note the legacy `/api/agents` LIST payload deliberately omits it (privacy) — expect null from `GetAgents`; the seed motive is echoed only on owner-scoped reads (the v1 characters REST surface and the legacy single-agent GET), which this SDK does not call. The owner-only `GET/PATCH/DELETE /api/v1/characters/{id}/motive` REST endpoints are NOT wrapped (dashboard/director tooling, not an in-game surface).
- voice_timeout: Implemented — server voice-lane idle release (SDK_CONTRACT.md): after no user speech for `VOICE_IDLE_TIMEOUT_S` the server emits `voice_timeout`, deletes the LiveKit room / closes STT, and KEEPS the socket (text keeps working; no disconnect follows — never wired into reconnect suppression). `EstuaryClient` clears the voice-mode gate and fires `OnVoiceTimeout(VoiceTimeoutData)`; `EstuaryManager` disposes the local LiveKit room WITHOUT `livekit_leave` (the room is already gone server-side; its Disconnected event during this teardown is expected, not a call failure) and forwards to `EstuaryCharacter`, which stops the mic and clears `IsVoiceSessionActive` so the next `StartVoiceSession()` is a fresh session. Recommended UX is the auto-mute illusion (mic shows muted; unmute = `StartVoiceSession()`). Belt-and-braces: any non-client LiveKit room disconnect also clears stale voice state via `HandleVoiceTransportClosed`.
- session_timeout: Implemented at EVERY reconnect-owning layer (Lens lesson 7/8: socket-layer suppression alone is insufficient) — `EstuaryClient.HandleSessionTimeout` fires `OnSessionTimeout(SessionTimeoutData)` and flags the disconnect that follows so the client's auto-reconnect is suppressed; the event is forwarded client → manager → character, and `EstuaryCharacter` sets its own `_serverEndedSession` flag so its component-level `autoReconnect` also skips the reap disconnect (it previously looped: reconnect → re-auth → billed voice resources → reaped again). Both flags clear on explicit connect. Resuming requires an explicit `ConnectAsync`/`Connect()` driven by user intent, per SDK_CONTRACT.md.
- session_rejected: Implemented — handles `session_rejected` {reason, cap, share_token_id}, fires `OnSessionRejected(SessionRejectedData)` (client → manager → character). The server disconnects immediately after, so the SDK sets the same `_serverEndedSession` suppression flag as session_timeout at BOTH the client and character layers — otherwise the trailing disconnect would auto-reconnect straight back into the concurrent-session cap in a loop. (Added 2026-07-15, upgrading the prior "impl deferred" status; the reconnect-loop was a real latent bug — no other SDK handles this event either.)
- moderation events (contract v1.14): Not implemented — documented gap. `moderation_warning` and `moderation_flag` are OPTIONAL server→client events; ignoring them is safe by design (the server already stopped further audio and redacted the transcript; the client just finishes its buffered audio). Worth implementing when product wants the UX: on `moderation_warning {level:"terminated"}` set the same `_serverEndedSession` reconnect-suppression flag as `session_timeout` (a disconnect follows immediately); on `moderation_flag` stop playback for that `message_id` (same mechanics as an interrupt) and replace the displayed text with `message`.
- input_limits / rate_limited (contract v1.13): No SDK change required — documented gap, deliberately. The server now truncates `text` and final STT transcripts to 4000 chars, ignores whitespace-only text, and drops over-rate messages (20 per 60s across `text`/`say_line`/transcripts) with `error {error: "rate_limited", message}`. All three are server-side and backward compatible: the existing `error` handler already surfaces `message`, and the session stays open, so a client that ignores the new `error` code behaves exactly as before minus the dropped turn. Worth adding only if product wants a distinct UI state — if so, read the optional `error` field and do NOT auto-retry (a retry loop is the one way to make this limit user-visible). A Unity client hitting 20 msg/min indicates a stuck send loop, not a human.
- character_model_loading: Implemented — runtime download + instantiation of a character's Estuary-generated 3D model (GLB) as a GameObject. `EstuaryModelLoader` (component) exposes `LoadForAgent(agentId)` and `LoadFromUrl(modelUrl, provider)`; it reuses `EstuaryHttpClient` (`GetAgents`/`PollModelStatus`/`DownloadGlb`) to resolve the ready GLB URL, downloads it, and instantiates via an **optional** glTF importer. The importer follows the LiveKit optional-dependency pattern exactly: `IEstuaryModelLoader` + `ModelLoaderBridge` (core) with a glTFast-backed impl in the define-gated `Estuary.glTFast` assembly (`ESTUARY_GLTFAST`, set by a `versionDefine` on `com.unity.cloud.gltfast`/`com.atteneder.gltfast`) — so the core assembly compiles with zero errors when glTFast is absent, and the loader surfaces a clear "install a glTF importer" error at runtime instead. Install via `Estuary > Install glTF Importer (glTFast)`. Provider-aware orientation offset (`AgentResponse.modelProvider` drives it): Tripo GLBs import facing -X in Unity, so the default `tripoRotationOffset` is `(0, -90, 0)` to face +Z — **verified live** against a real Tripo character (renders + textures + faces camera). Meshy default is identity (untested in Unity, corroborated by the frontend). Plus optional height normalization. Mirrors the web frontend's `Model3DViewer` flow (poll status → load textured `modelUrl`, fall back to `modelPreviewUrl` on `texture_failed`). NOTE: models load as **static meshes** — no glTF skeletal-animation playback yet (matches the frontend, which drives only procedural motion). **Verified end-to-end** 2026-07-16 in `estuary_unity_testing` against prod: GetAgents → DownloadGlb (~1.75MB) → glTFast import → instantiated `EstuaryCharacterModel`.
- simulation motives (contract v1.7): Implemented — `SimulationCharacterSpec`/`SimulationWorldCharacter` gain `Motive` (seed, optional ctor arg), `SimulationInstance` gains `CharacterMotives` (live per-run map), and the `/sim-v1` stream + `EstuarySimulation` component surface `OnMotiveUpdated(characterId, motive)` (`simulation_motive_updated`, wired like `OnWorldViewUpdated`). The director override `PATCH /instances/{id}/motives/{characterId}` is not wrapped in `EstuarySimulationApi` yet — add if a Unity-side director needs it (Estuarium's DM currently drives it from its own client).
- simulation (v1): Implemented — full public Simulation API (SDK_CONTRACT.md §REST API — Simulation (v1), contract v1.4–1.6). Three layers: `EstuarySimulationApi` (Core; coroutine REST client for `/api/v1/simulation/*` — worlds/instances CRUD, pair + group conversation triggers, events/lore/world-view/transcript reads; reuses `EstuaryHttpClient`'s auth internals so Bearer-token-vs-X-API-Key behavior is identical, and surfaces the server's `{"detail": ...}` body in error callbacks), `EstuarySimulationStream` (Core; `/sim-v1` Socket.IO namespace client reusing the SDK's built-in Socket.IO transport with auth `{apiKey, instanceId}` — streams `simulation_started/_message/_tool_call/_lore/_world_view/_complete/_error` for immediate triggers, main-thread queue + bounded reconnect like EstuaryClient), and `EstuarySimulation` (Component; owns both, pumps the stream queue in Update, exposes C# events + `TriggerConversation`/`TriggerGroupConversation`/`FetchWorldView`/`FetchLore` conveniences). Wire models in `Models/SimulationModels.cs` (Newtonsoft, camelCase `JsonProperty`, grouped in one file like AgentResponse.cs). Notes: the `/sim-v1` stream REQUIRES an API key (no Firebase token path server-side); scheduled (engine-processed) events do NOT stream — poll `ListEvents`; the world-view document arrives both as the `simulation_world_view` stream event and via `GetWorldView` REST (markdown null until the first conversation completes); request bodies serialize with NullValueHandling.Ignore because the server forbids unknown fields and defaults omitted ones. **Session isolation (contract v1.6):** sim lore/relationships/transcripts/world-view are per-instance, but remember-tool memories are keyed `(character, playerId)` and shared with live chat — so the component has a `worldId` field plus a `Destroy World On End` inspector toggle: `EndWorld()` tears down the stream and (when toggled) DELETEs the world server-side (v1.6 server purges instances, transcripts, AND memories), firing `OnWorldDestroyed`; a runtime `OnDestroy` fallback fires the DELETE fire-and-forget with the raw X-API-Key path (no coroutines during teardown; API-key-only because a TokenProvider can't resolve synchronously and falling back would escalate access; may be dropped on app quit — EndWorld() at a controlled moment is the guaranteed path). `ClearWorldMemories()` (component + Api, DELETE /worlds/{id}/memories → `SimulationWorldMemoriesCleared`) is the soft reset: wipes only sim-created memories, keeps the world/instances/lore/transcripts, never touches live-chat memories.
- turn_metrics: Not consumed (web-debug only) — backend emits this OPTIONAL/debug event (SDK_CONTRACT.md contract v1.2) carrying per-response voice-latency timings for the web chat latency gizmo; no Unity handler needed. Contract v1.2 adds an optional/nullable `speech_end_ms` field (predictive-turn head-start metric) and v1.12 adds an optional/nullable `tts_engaged_ms` field (when TTS synthesis started, vs. `tts_first_audio_ms` when its first byte arrived); both are additive and do not change the decision to ignore the event.
- animation_stream (`bot_animation`): Not implemented (auth opt-in only). The auth payload now carries the `enable_animation` flag (EstuaryConfig toggle, default false) so a developer CAN request ARKit-52 blendshape frames, but the Unity SDK does not yet consume/render `bot_animation` — the frames would be dropped. This matches every other SDK: the feature is EXPERIMENTAL and has no reference implementation anywhere (not even the TS SDK). Render support is a future item; requires a 16 kHz connect + server `ENABLE_A2F=true`.
- stt_config (`stt_provider` / `stt_language_hints` / `stt_context_terms`, contract v1.14): Not applicable — STT runs entirely gateway-side. The SDK ships 16kHz PCM and receives transcripts; which engine transcribes it (Deepgram Flux vs Soniox v5), which languages are hinted, and the character's custom vocabulary are per-character settings edited in the dashboard. `AgentResponse` does not model these fields and does not need to; a character configured for Soniox v5 with vocabulary terms behaves identically on the wire (SCRUM-232).
- encounter: Not implemented — the 2-character agent-to-agent Encounter (`subscribe_encounter` / `encounter_*` + `POST /api/encounters`) is Lens-Studio-only at MVP per SDK_CONTRACT.md. Add here if/when Encounter is promoted beyond the Lens SDK.
